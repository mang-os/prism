# Measured results

This report separates completed relevance comparisons from the longer performance protocol still open. Small machine-readable [result summaries](../benchmarks/results/README.md) are included in the repository. Raw per-query runs and HTML lab output live under ignored `artifacts/`; recreate them with the commands in the [README](../README.md). Numbers below are observations on one Windows 11 development machine, not general performance guarantees.

## Original marketplace fixture

The [fixture](../examples/marketplace) contains 180 documents and 90 queries in 30 intent groups, including 10 held-out groups (30 queries). The held-out split was fixed before scoring. These templated examples check product, service, and document intent behavior; they do not establish performance on an unseen business catalog. All values below use the held-out queries and top 10 unless marked as a subset. Model: `all-MiniLM-L6-v2`, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`, fingerprint `3fab1fe093079974341ee12ee9eb5e64334192c7231b9ad2867f6272816ac0e5`.

| Retrieval | nDCG@10 | Recall@10 | Semantic subset success@5 (10 queries) |
| --- | ---: | ---: | ---: |
| Exact lexical | 0.682 | 0.700 | 0.100 |
| Fuzzy lexical | 0.685 | 0.700 | 0.100 |
| Semantic only | 0.950 | 0.978 | 1.000 |
| Hybrid RRF | 0.832 | 0.900 | 0.500 |

The semantic-only branch retrieves all judged relevant results within the first ten on this fixture's semantic subset. Hybrid improves total recall over exact lexical, but ranks only half of semantic-subset queries successfully in the first five. The fixture's near-duplicate items and rank fusion with a lexical branch explain some of the loss. The report preserves those misses; no held-out labels or weights were changed after inspection. Synonym and combined-expanded lexical runs are also in the raw report.

Indexing all 180 documents, including embeddings, took **694 ms** in this run. The resulting one-segment vector index has **276,480 bytes** of vectors and **8,892 bytes** of mutation log. The corresponding lexical-only indexing run took **41 ms**. These times exclude model download and process startup. The lab's per-query p50/p95/p99 are in-process observations on 90 queries and are not the required HTTP latency distribution.

On the same 180-document fixture, the plain lexical index used 45,576 bytes of postings and 15,240 bytes of positions; the compressed index used 5,818 and 1,905 bytes respectively. Total bytes across the reported index files were 181,447 plain versus 126,740 compressed. The skip table remains a sizable fixed overhead on this small fixture.

## Public SciFact and OpenSearch

The public SciFact archive was checksum checked and prepared with **5,183 documents and 300 test queries**. Prism indexed the entire corpus with real 384-dimensional embeddings; the persisted snapshot contains **7,961,088 vector bytes**. The relevance run reused that snapshot, so its indexing-duration field is `null`. A separate fresh build with the same corpus and model took **72.2 s** to load the model, then **650.4 s** to accept all documents, including **649.5 s** inside document embedding, and **7.2 s** to publish the segment. Model download was excluded. The fresh index directory occupied **50,537,186 bytes**, including SQLite and segment files, and process RSS after the build was **803 MiB**. The tokenizer counted **3,681 documents** above the model's 256-token limit; their stored lexical text is complete but embeddings use a truncated prefix. This makes SciFact semantic quality especially sensitive to text ordering. See [dataset provenance](../datasets/README.md), [configuration](../benchmarks/configs/scifact.yaml), and the raw `artifacts/indexing/report.json` generated by [this script](../benchmarks/measure_indexing.py).

The matching **lexical-only** build took **0.221 s** to accept mutations and **9.162 s** to publish the segment, or **9.383 s total** (**552 documents/s** including refresh). Its index directory occupied **31,999,530 bytes** and process RSS after the build was **182 MiB**. This meets the 300 documents/s lexical reference target on this corpus, while semantic indexing is dominated by CPU embedding work. Its raw file is `artifacts/indexing/lexical-report.json`.

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Prism exact lexical | 0.5857 | 0.5583 | 0.6982 | 0.8676 | 0.6600 | 0 |
| Prism fuzzy lexical | 0.5901 | 0.5638 | 0.6982 | 0.8709 | 0.6600 | 0 |
| Prism semantic | 0.6451 | 0.6047 | 0.7833 | 0.9250 | 0.7533 | 0 |

The synonym-only and fuzzy-plus-synonym runs are also saved. SciFact has no curated synonym file, so synonym-only equals exact lexical. Hybrid improved recall@10 by 0.1137 absolute versus Prism exact lexical. OpenSearch lexical is a similar-capability reference; its raw scores are not compared to Prism's. The baseline used OpenSearch `3.3.0`, one primary shard, zero replicas, and a pattern tokenizer with lowercase filter. Prism uses Unicode NFKC plus casefold, so analyzer output can differ. Its title/body BM25 field scoring also differs in implementation details.

Representative `_analyze` calls on the pinned OpenSearch container confirmed the difference:

| Input | Prism tokens | OpenSearch tokens |
| --- | --- | --- |
| `Bluetooth Earbuds` | `bluetooth`, `earbuds` | `bluetooth`, `earbuds` |
| `Straße Café` | `strasse`, `café` | `straße`, `café` |
| `ＡＣ repair` | `ac`, `repair` | `ａｃ`, `repair` |
| `foo_bar` | `foo`, `bar` | `foo`, `bar` |

After restarting the same container for analyzer inspection, `docker stats` reported **1.112 GiB / 2 GiB** memory usage. This was a later observation, not simultaneous RSS during the original baseline; it must not be added to or subtracted from Prism's measured RSS.

The first Prism lexical run had in-process p50/p95/p99 of **672/1,227/1,392 ms**; OpenSearch's HTTP client measurements were **22/36/54 ms**. These are not equal measurement surfaces and expose a large Prism performance miss. A broad-query posting traversal was optimized afterward. A full 300-query rerun cut Prism exact lexical in-process latency to **141/353/489 ms** and hybrid to **191/475/654 ms**. Every top-100 ranking in all six Prism modes matched the first run exactly, with zero errors. The OpenSearch comparison remains tied to the same corpus and qrels, but its latency is a separate HTTP measurement. The initial fuzzy attempt exceeded its budget while constructing a BK-tree; the completed run used the bounded large-vocabulary lookup in [decision 0002](decisions/0002-bounded-fuzzy-candidates.md).

## Local HTTP load smoke after traversal optimization

This test used the same 5,183-document snapshot and 300 SciFact query texts through localhost HTTP. It warmed each mode/concurrency setting with 100 requests, then sent 1,000 measured requests with `top_k=10`, `candidate_k=100`, a **500 ms server deadline**, and fuzzy/synonym expansion disabled. Four server worker slots were available. Each setting ran sequentially. Percentiles below include only successful responses; error rates use all 1,000 requests and therefore matter as much as the percentiles.

| Mode | Clients | Successes | Error rate | p50 / p95 / p99 ms (successes) | Successful req/s | Server RSS MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Lexical | 1 | 988 | 1.2% | 156 / 396 / 471 | 5.49 | 592 |
| Lexical | 4 | 604 | 39.6% | 481 / 700 / 851 | 4.26 | 600 |
| Lexical | 16 | 198 | 80.2% | 1,081 / 1,516 / 1,728 | 3.39 | 602 |
| Hybrid | 1 | 984 | 1.6% | 172 / 374 / 463 | 5.10 | 626 |
| Hybrid | 4 | 412 | 58.8% | 529 / 763 / 907 | 2.64 | 633 |
| Hybrid | 16 | 123 | 87.7% | 1,180 / 1,621 / 1,809 | 2.00 | 633 |

At one client, Prism misses the specification's lexical p50/p95/p99 targets (20/75/150 ms) and hybrid p50/p95 targets (100/250 ms); the hybrid p99 success-only value is below 500 ms but has failures. Higher concurrency saturates the process; 429 overload rejections and deadline errors dominate. Client-observed success latency can exceed the server budget because network/queue/response time is also measured. This is a closed-loop smoke, not an open-arrival capacity test. The Docker OpenSearch service remained resident but idle during this test; its simultaneous RSS was not recorded. Server RSS above is the Prism process as sampled after each batch. The raw [load script](../benchmarks/load_test.py) and ignored `artifacts/performance/report.json` preserve counts and error codes.

## Synthetic scale probe

The [scale script](../benchmarks/synthetic_scale.py) created 50,000 short synthetic documents and deterministic **synthetic** 384-dimensional vectors. It is a storage/scan exercise only; it provides no semantic relevance evidence. Acceptance plus refresh took **11.16 s**, the index directory occupied **203.1 MB**, and process RSS after the run was **272 MiB**. After 20 warmups, 100 in-process queries per mode produced:

| Mode | p50 ms | p95 ms | p99 ms |
| --- | ---: | ---: | ---: |
| Lexical | 803 | 1,066 | 1,147 |
| Synthetic vector scan | 86 | 143 | 163 |
| Hybrid | 759 | 1,137 | 1,249 |

The repetitive synthetic terms create very long posting lists, exposing a Python lexical-scoring bottleneck. The vector figures show exact scan cost for 50,000 rows on this host, not model inference or real semantic retrieval. Raw settings and storage sizes are in ignored `artifacts/scale/report.json`.

## Measurement method and gaps

- Host: Windows build 26200, Intel Core i7-13620H (10 physical/16 logical cores), 16,786,550,784 bytes RAM, Python 3.11.16. The filesystem media and power mode could not be verified in this managed session. Prism and the Docker OpenSearch service shared this host, so their timing was affected by shared resources.
- Relevance uses graded qrels for nDCG and binary relevance for recall, MRR, and success. Unjudged documents count as nonrelevant. Candidate depth is 100.
- Every saved run records query text, split, subset, request settings, latency, hits, and metrics; the report records input checksums, OS, Python, model fingerprint, and index bytes. The local code state is currently uncommitted, so the report says `uncommitted`.
- The OpenSearch comparison is **lexical versus lexical**. Its BM25 parameters are `k1=1.2`, `b=0.75`, with title boost 2. Tokenization and scoring are close but not identical.
- A small in-process relevance run cannot support the specification's HTTP latency targets; the separate load smoke above does. Successful-response percentiles are subject to timeout selection bias.
- Repeated 10,000-request performance distributions, bounded-arrival testing, hosted CI, and reproduction from an actual Git clone are pending. A source-only copy did pass locked lexical installation and the documented ingest/refresh/typo-search path. The release definition of done remains open.
